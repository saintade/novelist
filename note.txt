FREE-TIER LIMITS (CHECKED 2026-09-11)
Supabase Free: 500 MB database, 1 GB files, 5 GB egress plus 5 GB cached egress;
projects can pause after one week of inactivity. Automatic backups are not
included. Render Free sleeps after 15 idle minutes and can take about a minute
to wake. It can restart at any time and has a shared 750 instance-hour monthly
allowance. Excess outbound/API traffic can suspend a free instance.

Free Render is suitable for this personal reader but does not guarantee long
unattended translation queues will finish while every browser is closed. Saved
results persist in Supabase; interrupted jobs recover on authenticated reconnect
within their attempt limit, while manually paused jobs stay paused. There is
no artificial keep-alive. GitHub Pages can host static UI, not this Node API.
Vercel would require adapting the worker to serverless/background infrastructure;
Render is the compatible free option for the existing server.

LIBRARY SIZE AND COMPRESSION
Read-only sample: 3 books, 682 downloaded chapters, 57 translation versions,
about 4.9 MB of chapter files and 6.9 MB of logical owner row payloads. Counts
grow as you read/download/translate. Database indexes and saved context add to
capacity; the 1 GB file allowance is not the only limit on book count.

PostgreSQL already compresses large text/JSON with TOAST/pglz. On local copies
of 61 translation rows, pglz used 2.61 MB versus LZ4's 2.83 MB, so pglz was kept.
No extra database compression extension was needed. New downloaded chapters
use gzip only when it saves at least 10%; a 30-chapter real-data sample saved
57%. Existing files are not rewritten. Readers support both forms, bound
decompression, and verify the same original-text SHA-256 hash after decoding.

TRANSLATION BEHAVIOR
Regular Translate/Retranslate submits a durable one-chapter job and returns
quickly. It can finish while you read elsewhere. Completion never redirects
another book; return to the requested chapter to load it. Transient failures retry
automatically, with three total attempts per unfinished chapter and backoff.
Quota/access/source errors or exhausted attempts stop; remaining reader recovery
controls affect only that reader job, not a bulk queue. Manual Pause/Cancel wins.

Bulk Translate supports adaptive groups of up to 10, or 1 for per-chapter
continuity. Translate untranslated reviews the whole indexed book (up to 20,000
chapters); manual ranges remain limited to 1,000. Download originals first.
Regular and grouped jobs may run on different chapters together.
Overlapping running chapters share work; completed matching versions are skipped.
Each result has a source ID/hash and ordered paragraph coverage. Fully closed,
validated chapters can be saved from token-truncated group output. Incomplete
chapters are not published. Only unfinished chapters retry, in smaller groups
after truncated output. Starting the job authorizes these bounded paid retries.
This uses the regular Responses API, NOT the discounted OpenAI Batch API.

Groups share pre-group recent context and guide instructions. New translations
and opt-in guide updates affect the next request; a 10-chapter group can pass
the default 5-chapter guide interval. Group output is capped by model and total
budget; Luna's application ceiling is 65,536 output tokens. Unknown models
default conservatively to 16,384. Group timing/usage averages are allocations,
not individually measured per-chapter latency or exact billing attribution.

Settings > Admin & usage shows monthly recorded cost estimates, unknown charges,
quota failures, open jobs and recent provider requests. One grouped request is
counted once, and retries have separate entries. New translation, guide, metadata
and term-suggestion requests are tracked; older history and other untracked tools
are not exact billing totals. The optional monthly alert is NOT a hard spending
cap. Remaining OpenAI credit is unavailable here; use the Usage/Billing links
for authoritative charges and provider limits.

For lower latency, compare gpt-4.1-mini and gpt-4.1-nano against Luna on a few
authorized chapters. Smaller non-reasoning models are useful speed candidates,
not a guarantee of equivalent translation quality. Luna already uses reasoning
effort none here. Ten chapters per request can improve throughput/input reuse,
but usually makes the first completed group take longer. No live paid speed
benchmark was run by the assistant.
